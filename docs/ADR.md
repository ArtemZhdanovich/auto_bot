# ADR — архитектурные решения (краткий реестр)

| # | Решение | Почему |
|---|---|---|
| 1 | Clean-слои + Dishka | сценарии тестируются фейками портов; транспорт тонкий |
| 2 | Один код в mono/micro (`services/*` на тех же роутерах) | постепенный рост без дублирования |
| 3 | Centrifugo: один личный канал на пользователя | мгновенный UI без подписок на каждый тред; масштаб (GrandChat-паттерн); namespaces в конфиге обязательны |
| 4 | Publisher в личные каналы участников, fire-and-forget | деградация без Centrifugo; полный MessageView в событии |
| 5 | S3-зеркало фото с индексом в ключе `NNN.jpg` | пережить удаление с источника; порядок гарантирован лексикографически |
| 6 | Lifecycle объявлений = конечный автомат в `listings.status` + placement-даты | модерация и монетизация ортогональны; версия правок pending_patch |
| 7 | Гибридная модерация: правила+risk score, ручная очередь, sampling партнёров | масштаб без штата; autoTrader-паттерн |
| 8 | Идемпотентность денег: условный `UPDATE payments` по статусу | двойной вебхук Telegram не продлевает дважды |
| 9 | Advisory-lock'и (pg_advisory_xact_lock) на гонки | join чатов, создание лотов, пакеты — без SELECT FOR UPDATE по строкам |
| 10 | Raw SQL UPDATE в ORM-сессии → ghost-объекты | асинхронный SQLAlchemy: после Core-UPDATE обновляй объект через ORM |
| 11 | Факт-парсеры по реальным данным БД (ДТП-строки encar двух семейств) | LLM-отчёты строятся на фактах, не на выдумке |
| 12 | Поэтапные compose-профили base→core→storage→workers→realtime→ai→micro | продукт жив на минимуме; периферия добавляется слоями |

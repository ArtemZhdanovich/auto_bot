# 04. План миграции без простоя

План рассчитан на один сервис в продакшене с живым трафиком (Telegram-бот,
Mini App, воркеры) и на команду из 1–2 разработчиков. Оценки — в
инженер-днях, ориентировочные.

**Базовое правило:** ни одна фаза не меняет контракт API и схему сообщений
так, чтобы старая версия перестала работать. Сначала «расширяем» (expand),
потом переключаем, потом «сжимаем» (contract) — в отдельном релизе.

---

## 0. Принципы и фича-флаги

| Флаг | Значения | Что переключает |
|---|---|---|
| `APP_ARCH_MODE` | `legacy` / `mixed` / `clean` | какой набор роутеров смонтирован (`create_app`) |
| `QUEUE_ENGINE` | `legacy` / `faststream` | кто потребляет очередь |
| `QUEUE_SHADOW` | `0` / `1` | дублировать публикацию в `*_v2` для теневого прогона |
| `USE_OUTBOX` | `0` / `1` | писать события в outbox вместо памяти |
| `FEED_CURSOR_V2` | `0` / `1` | отдавать `next_cursor` в ленте |

Флаги читаются из `Settings`, но **не должны** становиться вторым
источником правды: каждый удаляется после завершения соответствующей фазы.

Три обязательных условия старта:

1. Дерево собирается, тесты зелёные (фаза 0).
2. Есть бэкап БД и проверенный `deploy/restore.sh`.
3. Есть метрики: latency, error rate, размер очередей, DLQ.

## Фаза 0 — вернуть собираемость и зелёный baseline (0.5–1 дня)

**Цель:** `python -c "import app.main"` работает, `pytest` собирает все
модули, известно реальное число падающих тестов.

Шаги:

1. `app/api/dialog.py`: `RedisDep` импортировать из `app.core.deps_internal`.
2. `app/main.py`: удалить второй `app = FastAPI(lifespan=lifespan)`; передать
   `lifespan` в первый конструктор.
3. `tests/`: удалить 7 файлов-фрагментов **или** восстановить импорты и
   фикстуры. Решение: удалить как артефакты внешнего чата, а нужные сценарии
   переписать позже — иначе они маскируют отсутствие тестов.
4. Зафиксировать baseline: `pytest -q > baseline.txt` (число passed/failed/
   error). Это точка отсчёта для всех следующих фаз.

**Гейт:** `pytest --collect-only -q` без `ERROR`; `import app.main` без
исключений; `len(app.routes) > 60`.

**Откат:** правки в трёх файлах, откат `git checkout`.

## Фаза 1 — характеризационные тесты и наблюдаемость (2–3 дня)

**Цель:** зафиксировать текущее поведение, чтобы рефакторинг не менял
контракт незаметно.

Шаги:

1. Контрактные тесты на 10 самых нагруженных эндпоинтов: код, тело, схема
   (снимок OpenAPI в `tests/contracts/openapi.json`). Любое изменение схемы
   — осознанный diff.
2. Query budget фикстура (`tests/conftest.py`, см.
   [03-CHECKLISTS.md](03-CHECKLISTS.md#фикстура-query-budget-без-внешних-пакетов))
   и бюджет для `/api/listings`, `/api/favorites`, `/api/leads`.
3. `trace_id` в логах: middleware генерирует/принимает `X-Request-ID`,
   кладёт в `contextvars`, логгер добавляет поле. Это дешёвая замена
   OpenTelemetry на первом этапе.
4. Security-тесты как «красные»: IDOR, 401/403/422/429 — сначала падают,
   затем закрываются фазами 4 и 9.

**Гейт:** контрактные тесты зелёные на legacy; бюджеты записаны в
`docs/perf-baseline.md`.

**Откат:** только тесты, кода не касается.

## Фаза 2 — домен (3–4 дня)

**Цель:** вынести чистые сущности и порты, не меняя поведение.

Шаги:

1. `app/domain/shared`: `DomainError`, `DomainEvent`, `Money`.
2. `app/domain/{listings,favorites,leads,partners}`: сущности + `ports.py`.
3. Мапперы `ORM → domain` в `infrastructure/db/mappers.py`.
4. Правила из `services/*` переносятся в методы сущностей **по одному**:
   например, `Lead.claim()` вбирает проверки из `services/partners.py`.
5. Старые сервисы пока остаются и вызывают новые сущности — двойного
   поведения нет.

**Гейт:** домен не импортирует `sqlalchemy`, `fastapi`, `pydantic`,
`aio_pika` (проверка `ruff TID` / import-linter); unit-тесты домена не
поднимают БД.

**Откат:** новые пакеты не подключены к рантайму — удаляются без следа.

## Фаза 3 — UoW, DAO и репозитории на одном срезе (4–5 дней)

**Цель:** доказать схему на одном вертикальном срезе — избранное.

Шаги:

1. `BaseDAO`, `FavoriteDAO` с атомарным toggle (CTE) и keyset-страницей.
2. `SqlAlchemyUnitOfWork` + `OutboxDAO` (таблица `outbox`, миграция
   `0019_outbox` — только `CREATE TABLE`/`CREATE INDEX`).
3. `SqlAlchemyFavoriteRepository` реализует `FavoriteRepository`.
4. `ToggleFavorite`/`ListFavorites` — use cases.
5. Роутер `favorites` переписывается на use case, но **контракт сохраняется**
   (те же пути, коды, тело; `limit/offset` остаются, `cursor` добавляется
   опционально).
6. Старый код удаляется только после зелёных контрактных тестов.

**Гейт:** `test_favorites.py` (переписанный) зелёный; query budget ≤ 3;
повторный `POST` при гонке не даёт 500 (тест `asyncio.gather` × 10).

**Откат:** фича-флаг `USE_CASE_FAVORITES=0` возвращает старый роутер
(оба живут в одном релизе).

## Фаза 4 — use cases для listings/leads/auth (5–7 дней)

**Цель:** роутеры становятся тонкими; SQL уходит в DAO.

Шаги:

1. `ListListings`, `GetListing`, `GetFacets`; `enrich_listing_specs`
   выносится из `GET` в очередь `enrich_listing` (см. фазу 7).
2. `CreateLead`, `UpdateLeadStatus`, `GetLeadForPartner` — с проверкой
   владения внутри use case.
3. `AuthenticateTelegram`, `RefreshSession` — JWT-логика в
   `infrastructure/security`, use case оркестрирует.
4. Роутеры: только валидация входа, вызов use case, маппинг в схему.
5. `SessionDep` в роутерах больше не встречается (проверяется grep-тестом).

**Гейт:** `grep -r "SessionDep" app/transport/http/routers` пуст;
контрактные тесты и security-тесты зелёные; IDOR-тест на чужой лид → 404.

**Откат:** флаги по эндпоинтам, старые функции остаются в
`transport/http/routers/_legacy/`.

## Фаза 5 — Dishka параллельно с `Depends` (4–5 дней)

**Цель:** composition root, один контейнер на процесс.

Шаги:

1. `app/di/providers/*`: settings, database, redis, broker, repositories,
   use cases, security.
2. `app/app_factory.py::create_app(container=None)`: сборка приложения,
   `setup_dishka`, `lifespan` (warmup + close).
3. Роутеры переводятся на `DishkaRoute` + `FromDishka` **по одному**.
   Старые `Depends` работают рядом: `SessionDep` можно оставить как
   `Annotated[AsyncSession, Depends(...)]` до конца фазы.
4. Тестовый контейнер: `make_test_container()` с fake-провайдерами; тесты
   use case перестают использовать `FakeSession`.
5. Удаляются глобальные синглтоны: `engine` на импорте, `_publisher`,
   `@lru_cache get_redis` — переезжают в APP-скоуп.

**Гейт:** `create_app()` поднимается с тестовым контейнером без БД;
`pytest -m unit` не требует Postgres; в `app/` не осталось
`session_factory()` вне `infrastructure`.

**Откат:** `APP_ARCH_MODE=legacy` монтирует старый набор роутеров;
контейнер не создаётся.

**Подводный камень:** `DishkaRoute` не работает для websocket — если
появятся WS, использовать `@inject` вручную.

## Фаза 6 — outbox + FastStream publisher (5–6 дней)

**Цель:** события публикуются после commit, без потерь.

Шаги:

1. Таблица `outbox` уже есть (фаза 3). Включаем `USE_OUTBOX=1` для
   `LeadCreated`, `LeadClaimed`, `PaymentSucceeded`.
2. `BufferedEventPublisher` — для необязательных событий (аналитика).
3. `OutboxRelay` — отдельный процесс `worker_relay` (или таск в
   `worker_cron`), `FOR UPDATE SKIP LOCKED`.
4. `RabbitBroker` в APP-скоупе; `broker.publish(..., persistent=True)`.
5. Двойная публикация: `QUEUE_SHADOW=1` отправляет копию в `tasks.shadow`
   (fanout), которую читает теневой консьюмер и только логирует.

**Гейт:** тест «откат транзакции → в outbox нет строк → в брокере нет
сообщений»; тест «релей упал после publish → повторная публикация, консьюмер
не выполнил работу дважды».

**Откат:** `USE_OUTBOX=0`; таблица остаётся (не удалять в том же релизе).

## Фаза 7 — FastStream consumers: тень → cutover (5–7 дней)

**Цель:** заменить `TaskWorker` по одной очереди, не останавливая обработку.

Порядок: `fetch` → `send` → `enrich` → `cron`.

Шаги для каждой очереди:

1. Объявить `fetch_v2` (quorum, DLX) рядом с `fetch`.
2. Новый воркер `worker_fetch_v2` читает `fetch_v2` в режиме shadow:
   выполняет use case с `dry_run=True` (без записи), сравнивает результат.
3. Включить `QUEUE_SHADOW=1`: publisher пишет в `fetch` и `fetch_v2`.
4. Сравнить метрики 24–48 ч: количество сообщений, ошибки, latency,
   расхождения shadow-результатов.
5. Cutover: переключить publisher на `fetch_v2` (флаг), дождаться дренажа
   `fetch` (`x-message-ttl`/ручная проверка `message_count=0`), остановить
   старый воркер.
6. Переименовать `fetch_v2 → fetch` в следующем релизе (или оставить имя,
   задокументировав).

**Гейт:** DLQ не растёт; `message_count` старой очереди = 0; latency p95 не
хуже baseline; повторная доставка не создаёт дублей (`charge_lead` — 0
двойных списаний за окно наблюдения).

**Откат:** переключить publisher обратно на `fetch`; старый воркер держать
запущенным до конца фазы 8.

**Подводный камень:** нельзя запускать два консьюмера на одной очереди без
идемпотентности — они поделят сообщения и выполнят каждое один раз, но при
redelivery возможны дубли. Поэтому shadow — отдельная очередь, а не второй
консьюмер на той же.

## Фаза 8 — cron, DLQ replay, идемпотентность (3–4 дня)

**Цель:** убрать Redis-локи как единственную защиту и получить разбор DLQ.

Шаги:

1. `worker_cron` публикует `CronTick` с `idempotency_key = job:slot`.
2. `IdempotencyGuard` на Redis: `SET NX EX`; снятие ключа только при
   ошибке до commit.
3. CLI `python -m app.tools.replay_dlq --queue dead_letter --limit 100`:
   читает, логирует, опционально возвращает в исходную очередь.
4. Метрики: `queue_depth{queue}`, `dlq_depth`, `task_duration_seconds{job}`,
   `task_failures_total{job}`.

**Гейт:** рестарт Redis не приводит к повторному выполнению cron; replay
100 сообщений не создаёт дублей; DLQ виден в `/metrics`.

**Откат:** cron возвращается в `TaskWorker` (флаг `QUEUE_ENGINE=legacy`).

## Фаза 9 — безопасность и производительность (6–8 дней)

**Цель:** закрыть чек-листы, которые не входят в архитектурные фазы.

Порядок по риску:

1. S16/S17 rate limit на HTTP и internal API (429 + `Retry-After`).
2. S6 привязка Telegram-кода к браузеру; S14 ротация refresh.
3. S7/S8 output-схемы и `extra="forbid"`.
4. P1 `price_usd` + индекс; P2/P3 keyset и отказ от `count(*)` в ленте;
   P4/P5/P6 индексы.
5. P9 вынос `enrich_listing_specs` в очередь.
6. P10 единый `httpx`-клиент в боте.

**Гейт:** каждый пункт закрыт тестом, который падает на предыдущем коммите;
`EXPLAIN` для ленты — Index Scan, без Seq Scan на 100k строк.

**Откат:** миграции аддитивны; `price_usd` можно игнорировать, пока фича-
флаг `FEED_CURSOR_V2=0`.

## 3. Definition of Done

- `pytest -q` зелёный, 0 `ERROR`, покрытие домена и use case ≥ 80 %.
- В `app/domain` и `app/application` нет импортов фреймворков (CI-проверка).
- Ни один роутер не принимает `AsyncSession`.
- Все события денег идут через outbox; дубли исключены идемпотентностью.
- DLQ разбирается CLI, метрики очередей в `/metrics`.
- `docker-compose` поднимает старый и новый воркеры одновременно во время
  cutover; после фазы 10 — только новый.
- ADR и `docs/queues.md` описывают принятые решения и топологию.

## 4. Что может пойти не так

| Риск | Признак | План Б |
|---|---|---|
| Скрытые зависимости от `session.commit()` в середине сценария | тесты падают после переноса в UoW | разбить сценарий на два use case с явной границей |
| `lazy`-загрузка при добавлении связей | `MissingGreenlet` в проде | `lazy="raise"` + явные `selectinload` |
| Расхождение shadow-результатов | разные списки листингов | остановить cutover, сравнить SQL-логи, исправить до переключения |
| Потеря сообщений при cutover | `message_count=0`, но задач меньше | дренаж + replay из `dead_letter` |
| Долгая миграция индексов | блокировки на `listings` | `CREATE INDEX CONCURRENTLY`, окно низкой нагрузки |
| Усталость от флагов | 3+ флага на одну фичу | правило: флаг живёт не больше одной фазы |
